Why it matters

The chaos this replaces

Retail operations run on disconnected systems. This platform reconnects them into a single coordinated flow.

No more stale stock counts

Inventory updates the moment goods are received, moved, or sold. No weekly spreadsheets, and no more confusion where the store says three but the warehouse says ten.

Real time profitability

Every sale books revenue and matching cost of goods sold. The P&L is computed live from the ledger, not entered weeks later by an accountant.

Enforced approval workflow

A purchase order is not valid until the right person signs off. No more verbal approvals or forwarded emails. Every commitment is recorded, timed, and attributed.

Findability, guaranteed

Every unit is assigned a specific bin. Workers are directed by scan verified instructions. "Somewhere in the warehouse" is no longer an answer.

Accountability at the register

End of day, physical cash is compared against POS totals. Every shortage needs a manager's explanation, and patterns across cashiers are logged.

Resilience by design

If Financials goes down, sales still ring and goods still arrive. Events queue until the service recovers, so no single failure takes down the business.

Design principles

The rules that shape the architecture

Not conventions but enforced constraints. Every module in the system respects them.

Principle 01

Database isolation

No module may read another module's private data store. Each service owns its schema, its migrations, and its credentials. Cross service reads go through APIs, never SQL.

Principle 02

Independent deployment

A bug fix in the warehouse app must not force a redeployment of the POS system. Each module ships on its own schedule, on its own container, with its own environment.

Principle 03

Right protocol per conversation

Synchronous REST or gRPC when an answer is needed immediately. Asynchronous events when the caller just needs to announce that something happened and move on.

Principle 04

Resilience through queues

If one module fails, the others continue functioning. Events queue for the downed module to consume when it recovers, so no cascading outages.

Principle 05

Idempotent consumers

The bus guarantees at least once delivery. Every handler checks whether it has already processed a message before acting, combined with partial unique indexes for safety.

Principle 06

Transactional outbox

State change and event publication happen in the same database transaction. If the commit succeeds, the event will eventually be published. If it fails, the event vanishes with it.

Common questions

Frequently asked

Why not build this as a single application?

A monolith tangles point of sale logic, warehouse logic, and accounting logic into one codebase. Any change risks breaking unrelated functionality, and one bug can take down the whole business. Splitting by domain means each module can be developed, tested, deployed, and scaled independently. A failure in one leaves the rest of the operation running.

What happens if the Financials service goes down?

Nothing stops. Sales still ring, goods still arrive, pickers still pick. Financials' consumer queue holds every event until the service comes back online, then it processes the backlog and catches up. This is why the outbox pattern and durable queues matter.

How do two services talk to each other?

Two ways, chosen by the nature of the conversation. Synchronous REST or gRPC when one service needs an immediate answer to complete a transaction, like POS asking Inventory whether an item is available before accepting payment. Asynchronous events when a service just needs to announce that something happened, like Receiving publishing "goods received" and moving on without waiting for anyone to react.

What stops duplicate events from creating duplicate records?

Every event consumer is idempotent. Before acting on a message, the handler checks whether it has already processed a message with the same reference. Combined with a partial unique index at the database level, a second delivery produces zero side effects.

Can I run just one module in isolation?

Yes. Each module has its own database, its own migrations, and its own environment file. You can start just the Vendor Management service and its frontend, and the rest of the platform doesn't need to exist. Cross module calls fail gracefully if the other side isn't running.

How is feature rollout managed across phases?

Every module is wrapped in a feature flag (FEATURE_WAREHOUSE, FEATURE_FINANCIALS, etc). When a flag is disabled, all its routes return 404 and its frontend menu items are hidden. This lets new code merge to the main branch before the module is production ready, without exposing half built endpoints.

What's the point of the outbox table?

It solves a classic problem: how do you atomically save state and publish an event? If you commit first and then publish, a crash between the two loses the event. If you publish first and then commit, a rollback publishes a phantom event. The outbox table writes the event inside the same transaction as the state change. A background worker then drains it. Either both succeed or neither does.

Is this production ready?

The architecture is. The implementation covers the core domain flows end to end. Production hardening would add TLS between services, secret management, distributed tracing, backup automation, and a deployment pipeline. The infrastructure choices made here (Postgres, RabbitMQ, Docker) support all of those without architectural change.
